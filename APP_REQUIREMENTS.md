# Recipe Collector Web App — Requirements

## Overview

A simple web application that lets people collect, view, edit, and organize food recipes. Users can add recipes with ingredients and steps, browse their collection, search, and manage entries. v1 is a single shared or local collection (no accounts).

## Goals

- Make it fast to capture a recipe from memory or a cookbook.
- Make it easy to find a recipe later by name, ingredient, or tag.
- Keep the product small: no social features, no shopping lists, no meal planning in v1.

## Personas

- Home cook who wants a personal recipe box in the browser.
- Occasional user who pastes a recipe they already have written down.

## Scope (v1)

In scope:

- Create, read, update, and delete recipes.
- Structured fields for title, description, servings, time, ingredients, steps, tags, and notes.
- List and search the collection.
- Persist data so recipes survive a page reload.
- Basic validation and empty states.

Out of scope (v1):

- User accounts, auth, sharing, comments, likes.
- Import from URL / scrape third-party sites.
- Nutrition facts, unit conversion, scaling, timers.
- Image file uploads (optional image URL is allowed).
- Mobile native apps.

## Functional Requirements

### FR-1: Recipe data model

Each recipe MUST include:

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| id | string (UUID or similar) | yes | Generated by the app, immutable |
| title | string | yes | 1-120 characters, trimmed |
| description | string | no | Max 1000 characters |
| servings | positive integer | no | 1-100 if present |
| prepTimeMinutes | non-negative integer | no | |
| cookTimeMinutes | non-negative integer | no | |
| ingredients | list of ingredient lines | yes | At least 1 |
| steps | list of instruction strings | yes | At least 1 |
| tags | list of short strings | no | Lowercased, unique, max 20 tags |
| notes | string | no | Max 2000 characters |
| imageUrl | string (URL) | no | Optional; display if valid-looking URL |
| createdAt | ISO-8601 datetime | yes | Set on create |
| updatedAt | ISO-8601 datetime | yes | Set on create and every update |

Each ingredient line MUST include:

- `name` (required, 1-200 characters)
- `quantity` (optional string, e.g. `2`, `1/2`)
- `unit` (optional string, e.g. `cup`, `g`)

Acceptance:

- Creating a recipe without title, ingredients, or steps is rejected with a visible field-level error.
- Empty title after trim is treated as missing.
- `id`, `createdAt`, and `updatedAt` are never editable by the user.
- Duplicate tags on one recipe are stored once.

### FR-2: Create recipe

The app MUST provide a New recipe action that opens a form.

Acceptance:

- Form includes all editable fields from FR-1.
- Ingredients and steps are editable as a dynamic list (add / remove / reorder).
- User can add at least 20 ingredient lines and 20 steps.
- Submit with valid data saves the recipe and navigates to the recipe detail view.
- Submit with invalid data does not save; errors appear next to the failing fields.
- Cancel / back discards unsaved changes after a confirmation if the form is dirty.
- After save, the recipe appears in the collection list without requiring the user to re-enter data.

### FR-3: List recipes

The home / collection view MUST list all saved recipes.

Acceptance:

- Each row/card shows: title, up to 3 tags, total time if prep+cook are set (prepTimeMinutes + cookTimeMinutes), and servings if set.
- Empty collection shows a message and a primary Add your first recipe action.
- List is sorted by `updatedAt` descending by default.
- Clicking a card/row opens that recipe detail view.
- Collection of 50 recipes renders without layout breakage; titles wrap or truncate with ellipsis.

### FR-4: View recipe detail

Acceptance:

- Detail view shows all fields that have values; empty optional fields are hidden (not shown as null).
- Ingredients render as a list; quantity, unit, and name appear on one line when present (e.g. `2 cups flour`).
- Steps render as a numbered list in stored order.
- Actions available: Edit, Delete, Back to collection.
- Missing recipe id (unknown or deleted) shows a not-found message and a link back to the collection.

### FR-5: Edit recipe

Acceptance:

- Edit form is prefilled with current values.
- Saving updates `updatedAt` and preserves `id` and `createdAt`.
- Validation rules match create.
- After save, detail view shows the new values.
- Cancel returns to detail without changing stored data.

### FR-6: Delete recipe

Acceptance:

- Delete requires confirmation (dialog or equivalent) naming the recipe title.
- Confirming removes the recipe from storage and returns to the collection.
- The deleted recipe no longer appears in list or search.
- Canceling confirmation leaves the recipe unchanged.

### FR-7: Search and filter

Acceptance:

- A search box filters the collection as the user types (debounce of 300ms or less is acceptable).
- Match is case-insensitive against title, ingredient names, and tags.
- No matches shows an empty-state message including the query text, not a blank page.
- Clearing the query restores the full list.
- Optional tag chips: clicking a tag on a card or detail filters the list to recipes with that tag.

### FR-8: Persistence

Acceptance:

- Recipes persist across browser refresh.
- Acceptable v1 storage: localStorage, IndexedDB, or a simple backend with a file/db.
- If storage quota fails, the user sees an error and in-memory data is not silently dropped without notice.
- Reloading after create/edit/delete reflects the last successful write.

### FR-9: Navigation and information architecture

Acceptance:

- Primary screens: Collection, Recipe detail, Create, Edit.
- User can reach Collection from every other screen in one action.
- Browser back button works for detail to list and edit to detail (or list).
- Page titles (document title or visible heading) identify the current screen, e.g. Recipes, Pancakes, New recipe.

## UI / UX Requirements

### UX-1: Layout

- Usable viewport: 360px to 1440px wide.
- Collection is a responsive grid or list; on viewports under 640px, single column.
- Forms are readable without horizontal scrolling at 360px.

### UX-2: Feedback

- Primary actions (Save, Delete confirm) show a loading or disabled state while the write is in progress; double-submit does not create duplicate recipes.
- Successful save shows brief confirmation (toast or inline) or immediate navigation to the updated detail.
- Destructive action (delete) is visually distinct from Save (e.g. different color or placement).

### UX-3: Accessibility

- All form fields have visible labels.
- Buttons and links are keyboard reachable; focus order follows visual order.
- Confirmation dialogs trap focus until dismissed.
- Contrast meets WCAG 2.2 AA for text and interactive controls.
- Images from `imageUrl` use the recipe title as alt text; broken URLs fail gracefully (hidden or placeholder).

### UX-4: Empty and error copy

- Empty collection: No recipes yet plus a CTA.
- Invalid URL on image is ignored for display; form may warn but MUST still save other fields.
- Generic storage/network failure: Couldn't save your recipe. Try again. (or equivalent). No stack traces in the UI.

## Non-Functional Requirements

### NFR-1: Performance

- First meaningful collection view in under 2s on a local/dev machine with 50 recipes or fewer.
- Search filtering of 50 recipes feels instant (under 100ms after debounce).

### NFR-2: Reliability

- No data loss on refresh after a successful save.
- App does not crash the tab on malformed stored JSON; it shows a recovery message and may reset or skip bad records.

### NFR-3: Privacy (v1)

- If using only browser storage, no recipe content is sent to a server.
- If using a backend, v1 may be a single shared dataset; this MUST be documented in the README as not private/multi-user.

### NFR-4: Browser support

- Latest two versions of Chrome, Firefox, Safari, and Edge.
- No IE11 support.

### NFR-5: Code quality

- Runnable from the repo with documented install/start steps in README.
- Core flows (create, list, view, edit, delete, search) are manually testable without special fixtures.

## Acceptance Criteria (end-to-end)

The following scenarios MUST pass on a clean install:

1. **First recipe**
   - Open app, empty state visible, New recipe, fill title Tomato Soup, one ingredient tomatoes, one step Simmer, Save.
   - Detail shows title, ingredient, and numbered step.
   - Refresh, same recipe still present.

2. **Collection growth**
   - Add a second recipe Grilled Cheese with tag lunch.
   - Collection shows both; most recently updated first.

3. **Search**
   - Query tomato shows Tomato Soup only.
   - Query lunch shows Grilled Cheese only (tag match).
   - Query xyz-no-match shows empty search state.

4. **Edit**
   - Edit Tomato Soup, add a second step, save.
   - Detail shows two steps; updatedAt is newer than createdAt.

5. **Delete**
   - Delete Grilled Cheese, confirm.
   - Collection has only Tomato Soup.
   - Refresh, still only Tomato Soup.

6. **Validation**
   - New recipe with blank title and no ingredients/steps cannot be saved; errors shown.
   - Adding title plus 1 ingredient plus 1 step then allows save.

7. **Not found**
   - Opening a bogus recipe URL/id shows not-found, not a blank crash.

## Open Decisions (defaults if unspecified)

- **Stack:** Any simple web stack (static HTML/JS, or one common framework). Document the choice in README.
- **Identity:** No login in v1. Single local (or single-server) collection.
- **Images:** URL only; no file upload.
- **Units:** Free-text units; no unit ontology required.

---

## Success Definition

 v1 is done when a new user can add several recipes, find them by name or ingredient, edit and delete them, and see the same data after refresh — with the e2e acceptance scenarios above passing and this document's field/validation rules respected.
